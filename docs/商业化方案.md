# 深圳保障房提醒 · 商业化方案

> 2026-10-21 实现更新：当前采用全市群，可扩展多个接收相同内容的全市群。下文旧版单区群、自动可查和概率话术不能直接当作当前交付承诺；以 [多群运行与修复说明](多群运行与修复说明.md) 为准。查询页人工上传并登记版本后才标为可查，供需比例不是个人成功概率。

> 本文是这个业务的操作手册：卖什么、怎么卖、怎么交付、怎么收钱、出问题怎么办。
> 代码和数据都在 `D:\HousingBot`，换电脑只搬这一个目录。

## 一、卖的是什么

**不是"通知"，是"替你盯着 + 提醒你下一步"。**

买家的真实处境：深圳 11 个区各自发通告，域名不同、栏目不同、格式不同；一个批次从发布到签约要走六七步，每一步都有截止时间，漏一步就要再等半年。

他自己刷得到的，是"有没有新房源"。
他刷不到的，是"**我报的那一批，现在走到哪一步了**"。

这就是产品的立足点。

### 只有一档：单区管家版

**一个买家，一个区，一档服务。** 不卖基础版，也不卖全市版：买家的户口和轮候区是固定的，别的区的房源对他没有意义，推了只会让他觉得吵。

| 服务 | 内容 |
|---|---|
| 新通告即时推（微信） | 本区所有保租房/公租房通告，30 分钟一轮 |
| 每日 08:30 早报 | 正在认租 / 即将截止 / 新增 / 腾退 |
| 认租截止前 3 天、1 天提醒 | 只在本区有批次时发 |
| 批次全流程追踪 | 认租→核查→摇号→选房→签约，走到哪一步 |
| 资格粗筛 | 面向个人/企业、户籍、社保年限、收入限额 |
| 摇号结果即时推 | 多少人抢多少套 + 官方名单 PDF 链接 |
| 排位查询 | 群里给查询页链接，买家自己输入认租编号看队列和排第几 |
| 上车预测 | 按公开房源数和名单算"能不能选到房"，给依据和逐队列概率 |
| 覆盖范围 | **仅买家所在区**（市级面向全市的批次照推，不漏） |

> 资格粗筛只做**提示**，不做**判定**。系统不会告诉买家"你一定符合"，只会说"这批要求深户 + 社保满 5 年"。
> 理由：资格规则每年调整，替人下结论一旦说错就是退款和投诉。

### 建议定价

| 档位 | 价格（单区） |
|---|---|
| 7 天试用 | 9.9（可抵首月） |
| 月付 | 19.9 |
| 季付 | 49 |
| **年付（主推）** | 158 |

年付是重点：现金流最好、客服成本最低、续费谈判一次管一年。首月用 9.9 换评价，第二个月起按上面报价。

## 二、交付形态：买家什么都不用装

这是整套方案最重要的设计。

```
买家：闲鱼下单 → 收到一张群二维码 → 微信扫码 → 加群 → 结束
```

**不装软件、不注册账号、不看教程、不填表单。** 全部操作 30 秒，唯一动作是「扫一下」。

### 为什么用 PushPlus 群组

- 我们只有一个人、一台电脑，做不了"每个买家一个推送通道"。
- PushPlus 的 `topic`（群组）支持**一条请求发给全群**，成本恒定。
- 私密群组只有通过群主二维码加入的人才能看内容，天然就是个付费门槛。

### 群组矩阵

**一个总群就够了**：`深圳-管家`，`regions: []` 表示收全市通告。

```json
{ "name": "深圳-管家", "label": "深圳 · 管家版", "tier": "pro", "topic": "<群组编码>", "regions": [] }
```

为什么不按区拆：分区群的硬伤是**本区当天没批次，群里就只有"暂无"**。2026-10-21 光明群就是这样——0 批正在认租、0 条新增，只剩一条摇号结果，新入群的人会以为群是死的。一个总群无论哪天都有其他区的内容，不会显得死；买家靠标题里的区名（"光明区 2026第1批 保租房"）找到自己那一批。

10 个区群配置仍然保留在 `data/groups.json`，`topic` 清空即跳过。将来某个区买家多到值得单独建群，填回 `topic` 和 `regions` 就能恢复分区推送——`regions: []` 和 `regions: ["光明区"]` 走的是同一套 `covers()` 逻辑。

市级通告（`level=city`）无论分区与否都会发给所有群。

#### 加入后回复（PushPlus 群组设置）

```
你好，欢迎加入深圳保租房·公租房管家群。

① 每天 08:30 一条早报：全市各区在途批次的认租截止、核查、摇号、选房进度，找到你所在区那一行就行。
② 有新通告（新批次、核查名单、摇号结果、选房通知、签约）30 分钟内单独推，标题里带区名。
③ 认租编号可自助查队列和排位：{HOUSING_LOOKUP_URL}

平时一天 1~2 条，有新政才多发。不发广告，不收集个人信息。
内容来自政府官网，个人整理，非官方，以原文为准。
```

三句话对应三个最容易流失的点：怕群是死的（说明每天固定有早报）、怕刷屏（给出条数）、怕信息被收集（只按认租编号算排位）。域名备案下来后只需要把 `{HOUSING_LOOKUP_URL}` 换成短域名。

## 三、运行机制

### 三个定时任务

| 任务 | 时间 | 作用 | 发到哪 |
|---|---|---|---|
| `HousingBot-Scan` | 07:00 起每 30 分钟，共 15.5 小时 | 抓 25 个官网，新通告即时推 | 全部启用的群 |
| `HousingBot-Digest` | 每天 08:30 | 早报：正认租/新增/腾退 | 全部启用的群 |
| `HousingBot-Remind` | 每天 20:30 | 只做认租截止提醒（流程节点已由 Scan 即时推） | 全部群（都是管家版） |

> 电脑关机时的空档，由任务计划的 `StartWhenAvailable` 在开机后补跑一次。
> 通告不是秒级需求，晚几小时完全可以接受 —— 这一点要在商品页写清楚，别让买家误以为是实时行情。

### 额度

PushPlus 免费实名账号：**微信渠道 200 条/日、同一分钟最多 5 条**。

实际消耗：
- 一次扫描最多 1 条/群。开了 3 个群 = 3 条。
- 早报 1 条/群。
- 提醒只在有批次临近截止或阶段推进时才发，一天通常 0–2 条/群。

按 3 个群估算，一天 10 条左右，**离 200 还很远**。等群开到 15 个以上、每天新通告又多时，再考虑买会员（2000 条/日）。

### 摇号结果与"能不能上车"

批次从"认租结束"到"选房"之间会发一份**公证摇号结果**，这是买家的情绪高峰：名单几千人，他只想问两件事——多少人抢多少套、我排第几。

系统扫到这类通告会自动做三件事：

1. **解析附件**（PDF/Excel），按户型档统计认租人数、各队列人数、顺序号区间；
2. **对上房源数**（配租通告里的《房源概况》），算每档、每个队列的平均机会；
3. **推送里直接给结论**，例如 `40㎡：房源 111 套 / 认租 3,744 户 → 平均约 3.0%`，逐队列列出，并把官方名单 PDF 挂成可点链接。

> 名单里有姓名和掩码证件号。系统**只存聚合数字**（人数、队列分布、顺序号区间），一行个人信息都不入库；
> 买家发来认租编号时，是现下现算、算完即弃。这条规则写死在代码里，不靠运营自律。

**必须讲清楚的一点**：公告原文写了"公证摇号顺序号并非最终选房顺序"。深圳规则是**先队列、后顺序号**——第一队列全部走完才轮到第二队列，同队列内才按顺序号。推送里每次都带这句，避免买家以为 1 号就稳。

#### 回答"我排第几"：自助查询页，不进群主私聊

**买家自己查，不用问群主。** 摇号结果推送里带一条查询页链接，买家输入认租编号就能看到：

```
批次：光明区 2026年第一批次面向个人配租保障性租赁住房公证摇号结果
你认租的是：40㎡左右的房源（单身公寓类）
队列：第一队列 · 摇号顺序号 123（本档共 3,744 户）
本档房源：111 套
  · 第一队列 330 户 → 剩 111 套
  · 第二队列 741 户 → 剩 0 套
  · 第三队列 2,673 户 → 剩 0 套
你在本队列排第 123 位
结论：候补靠前——前面约 12 户放弃就有机会，值得等
```

查询页是 `tools/build_lottery_lookup.py` 生成的**纯静态 HTML**（数据内嵌、不发请求），
每区一份，文件里只有「认租编号 → 队列/顺序号/排位」，**不含姓名、不含证件号**。

> **队列可以改**：摇号名单表头写的是「队列分类（非最终）」，资格核查后队列可能变。
> 页面默认显示名单上的队列，用户点「第一/第二/第三队列」按钮就按选中的队列重算排位和结论；
> 各队人数仍来自名单标注，页面已注明仅供参考。

```powershell
# 每批复核后刷新一次（建议放进每日收尾动作）
# --days 900：至少要覆盖到去年的两批，否则重跑会把老批次从页面里挤掉
# --all-districts：库里有摇号名单的区逐个生成（现在是 7 个区），最后自动重建入口页
.\.venv\Scripts\python.exe -m tools.build_lottery_lookup --all-districts --days 900
# 单区调试仍然可以指定区名
.\.venv\Scripts\python.exe -m tools.build_lottery_lookup --district 光明 --days 900 --out lookup/guangming.html
```

**防转发**：页面带日期门禁。推送里的链接是 `入口页?d=YYYYMMDD`（北京时区，由 `render.lookup_url_for`
自动拼），页面在标注当天起的7个北京时间自然日内显示查询框。例如2026-10-23链接可用至2026-10-29结束。
缺少、无效、未来或超过有效期的日期分别提示。落地页的区按钮透传原始 `d`，不会因跳转而延长有效期。
这是前端日期提示，修改参数可以绕过，不提供会员鉴权或真正的访问权限控制。

托管使用**腾讯云 CloudBase 静态托管**：默认域名适合测试，可能出现访问提示、频率限制或微信外链封控；正式使用建议配置自定义域名。微信外链拦截与本项目日期门禁是不同问题，延长有效期不能解除微信拦截。参考官方[默认域名说明](https://docs.cloudbase.net/service/alias)及[微信封控处理](https://docs.cloudbase.net/lowcode/faq)。

1. 腾讯云控制台开通「云开发 CloudBase」→ 新建环境（按量计费）→ 记下环境 ID；
2. 环境内开启「静态网站托管」；
3. `npm i -g @cloudbase/cli` → `tcb login` → 把 `lookup/` 上传到根目录；
4. 用默认域名在手机微信里打开一次，确认可用。

然后把**入口页**地址写进 `.env`（不是某个区页）：

```ini
HOUSING_LOOKUP_URL=https://你的环境域名/
```

推送里的链接统一指向入口页，买家自己选区；以后有新区的摇号名单入库，重跑
`--all-districts` 再上传即可，不用改代码。
`HOUSING_LOOKUP_URL` 留空时这一行不出现——不承诺一个打不开的入口。

> 隐私边界：区页内嵌整批认租编号，理论上可以顺序枚举，但页面里没有姓名和证件号；
> 入口页写明用途和"非官方"。等付费用户上量后，再考虑按批随机目录名或改成服务端查询限流。

群主自己仍可用 CLI 兜底（买家截图发来、页面打不开时）：

```powershell
.\.venv\Scripts\python.exe -m app.housing.cli predict --apply-no SQ2026BZ360007741
```

没有编号也能演算：`predict --queue 第一队列 --order 500 --category 40`。

**话术边界**：只说"按公开数据估算"，不说"你一定能选到"；每次附三个不确定项（放弃率、资格核查淘汰、具体项目/朝向差异）和官方原文链接。

#### 批次全流程追踪：五步都收、都推

一条批次的生命周期是固定的，买家最容易焦虑的恰恰是"后面还有没有人管我"：

| 步骤 | 典型标题 | 推送方式 |
|---|---|---|
| 认租 | 配租有关事项的通告 | 即时推 + 截止前 3 天/1 天提醒 |
| 资格核查 | 认租资格核查结果的公示 | 即时推（标"第 2 步"） |
| 摇号 | 公证摇号结果的通告 | 即时推，带人数/房源/概率/查询页 |
| 选房 | 选房名单及选房签约的通告 | 即时推（标"第 4 步"） |
| 签约 | 签约有关事项的通告 | 即时推（标"第 5 步"） |

每条流程推送都带一行进度条，例如
`认租✅ → 资格核查✅ → 摇号✅ → 选房🔵 → 签约⚪`，
买家一眼知道自己那批走到哪、下一步等什么。

注意：**公租房没有公证摇号**（按轮候排序选房），进度条自动省掉摇号这一步，
不会凭空多出一格。用 `cli batches --region 光明` 可以核对每批五步齐不齐。

#### 同一份推送，服务四种人：靠"对号入座"排版

群推送是广播，没法按人发。所以每条消息都按固定结构写，让每个人自己找到那一行：

1. **标题 = 区 + 批次 + 阶段**（如 `【光明区 · 2026第1批】摇号结果已公布`），1 秒判断跟自己有没有关系；
2. **正文有"你现在要做的"**，2–3 条带条件的短句，每条都写"不属于这类就忽略"；
3. **早报是唯一的全局视角**，每个在途批次一行：

```
· 2026第2批 保租房｜认租中｜11-07 18:00 截止｜没交的尽快交
· 2026第1批 保租房｜选房｜时间见原文｜按场次到场，逾期视为放弃
· 2025第4批 公租房｜签约｜时间见原文｜已选房的去签约
```

四种人的落点：

| 你现在的状态 | 会收到什么 | 要做什么 |
|---|---|---|
| 还没认租 | 新批次发布 | 符合就去认租、保存认租编号；不申请忽略本条 |
| 认租了、没摇号 | 资格核查结果 | 在名单里等摇号；不在的按期复核 |
| 摇号结果已出 | 摇号结果 + 查询页 | 输入认租编号查队列和排位 |
| 已进选房名单 | 选房通知 | 按附件场次到场，逾期视为放弃 |

**查询链接只在真能查到的时候出现**：摇号结果消息、保租房选房消息。公租房没有公证摇号，
查询页里没有这批数据，链接自动隐藏。

**选房场次不解析**：PDF 抽错一次就可能让人跑错日期，消息只写"场次见附件，以原文为准"。

## 四、日常操作（你每天要做的）

```powershell
cd D:\HousingBot

# 看今天抓到了什么、有没有待推
.\.venv\Scripts\python.exe -m app.housing.cli scan --dry-run --pages 1

# 正式扫描并推送（计划任务会自动跑，手动补跑用这个）
.\.venv\Scripts\python.exe -m app.housing.cli scan --deliver

# 看早报内容，不发
.\.venv\Scripts\python.exe -m app.housing.cli digest --dry-run

# 管家版提醒：先看有哪些，再决定发不发
.\.venv\Scripts\python.exe -m app.housing.cli remind --dry-run
.\.venv\Scripts\python.exe -m app.housing.cli remind --deliver

# 当前在租的批次（回答买家"现在有哪些"最快的方式）
.\.venv\Scripts\python.exe -m app.housing.cli list --open

# 批次全流程追踪：每批走到哪一步、缺哪一步
.\.venv\Scripts\python.exe -m app.housing.cli batches --days 120

# 群主兜底：买家报认租编号，查队列/排位/能不能上车
.\.venv\Scripts\python.exe -m app.housing.cli predict --apply-no SQ2026BZ360007741

# 刷新自助查询页（改了名单解析规则或新批次入库后）：所有区 + 入口页一次生成
.\.venv\Scripts\python.exe -m tools.build_lottery_lookup --all-districts --days 900

# 摇号结果解析情况（新批次扫到会自动解析，这条用来看有没有漏）
.\.venv\Scripts\python.exe -m app.housing.cli lottery --show

# 改过解析规则后，给历史通告重新算一遍（不重抓正文）
.\.venv\Scripts\python.exe -m app.housing.cli lottery --backfill --days 180 --force

# 哪些群在生效
.\.venv\Scripts\python.exe -m app.housing.cli groups
```

**每天固定动作（5 分钟）：**
1. 早上看一眼早报有没有正常发出；
2. 有人下单 → 问清户口所在区 → 私聊发对应区群二维码 → 订单备注区名；
3. 到期前一天私聊提醒续费，不续的发新码、把老成员移出群。

## 五、换电脑怎么搬

**只搬一个目录：`D:\HousingBot`。**

| 内容 | 处理 |
|---|---|
| `app\` `data\` `.env` `scripts\` | 直接拷到新电脑同一位置 |
| `.venv\` | **不能拷**，虚拟环境写死了旧机器路径。新电脑跑一次 `scripts\setup.ps1` 重建 |
| 计划任务 `HousingBot-*` | **不会跟着走**，新电脑上重跑 `scripts\install_housing_tasks.ps1` |
| `logs\` | 可拷可不拷 |

新电脑首次部署：

```powershell
# 1. 安装 Python 3.10 64 位（勾选 Add to PATH）
# 2. 把整个 HousingBot 目录拷过来，删掉 .venv
# 3. 执行：
powershell -ExecutionPolicy Bypass -File .\scripts\setup.ps1
# 4. 注册计划任务
powershell -ExecutionPolicy Bypass -File .\scripts\install_housing_tasks.ps1
```

## 六、闲鱼上架

### 标题（关键词决定流量）

> 深圳保障性租赁住房提醒 保租房公租房认租通知 光明龙华南山宝安 微信推送

闲鱼流量九成来自搜索。**一个区一个商品链接**，每个标题带各自的区名，覆盖不同搜索词。

### 首图

一句话打痛点，别放 Logo：

> 「光明区又放了一批保租房，你还不知道？」
> 每 30 分钟盯 25 个官网 · 新通告直接推微信

### 详情页结构

1. **你在错过什么** —— 举一个真实案例（例：10 月光明区放 393 套，认租窗口只有 9 天）
2. **我做什么** —— 25 个官网、11 个区，30 分钟一轮
3. **你会收到什么** —— 贴真实推送截图（链接可点的那种）
4. **服务清单** —— 一个区一档价，列清每天会收到什么
5. **怎么开通** —— 加个人微信 → 免费拉进本区群看 3 天 → 满意再拍单
6. **常见问题** —— 要装软件吗？不要。要注册吗？不要。手机要一直开着吗？不要。
7. **声明** —— 本服务仅整理政府公开信息，非官方产品，不承诺任何申请结果

### 主路径：个人微信 + 免费 3 天

陌生人不扫群码，通常四个顾虑：码是陌生人的、私密群看不到内容、怕进群被推销、群二维码 7 天过期。

```
闲鱼/小红书看到 → 加个人微信（有朋友圈、有真人）→ 免费拉进本区群
→ 先看 3 天真实推送 → 第 4 天再谈 9.9/19.9
```

为什么比直接甩群码好：

- 个人微信有朋友圈、头像、聊天记录，比一张孤零零的二维码可信；
- 免费 3 天把"扫码风险"变成"先看看"，决策成本接近 0；
- 顺带解决群码 7 天过期：由你手动拉人，不依赖二维码；
- 续费、答疑、退款都在同一个对话里，复购率高。

商品页要写清"接下来会发生什么"：

> 加微信后我会拉你进光明区群，不推销、不发广告；
> 先免费看 3 天，满意再拍；7 天内不满意全额退。
> 推送由 PushPlus 公众号发出，不是陌生微信群。

### 信任物料清单

- 打码的真实推送截图（保留链接可点的样子）
- 往期批次回顾：证明你懂深圳规则（先队列后顺序号、公租房没有摇号）
- 查询页 demo：用假编号演示，别贴真实买家编号
- 买家评价/成交记录截图（征得同意）
- 群公告：只发本区通告、不发广告、非官方、免责声明

合规红线：不用"官方""包中签""保证选房"等表述；收款走平台或留退款记录。

### 每日动作

- 点一次「擦亮」（免费曝光刷新）
- 回复所有咨询，5 分钟内回
- 新成交的私聊要一句好评

## 七、推销

按投入产出排序：

1. **闲鱼搜索词覆盖** —— 成本最低。一个区一个链接。
2. **小红书/知乎攻略文** —— 《深圳保租房认租全流程》《我怎么蹲到光明那批 393 套的》。正文讲干货，结尾一句"放盘提醒我做了个小工具，评论「提醒」"。这是唯一能带真实流量的免费渠道。
3. **精准群** —— 深圳租房群、公租房轮候群、豆瓣深圳租房小组。先答疑再留联系方式，直接发广告会被踢。
4. **老带新** —— 推荐一个成交送一个月。成本几乎为零，转化最高。

**别做**：刷单、买流量、群发广告。闲鱼对虚拟服务风控很严，一封号前面的积累全没了。

## 十、风险清单

| 风险 | 应对 |
|---|---|
| 你的电脑挂了 | `StartWhenAvailable` 补跑；商品页写清推送时段；有条件就上旧笔记本专机 |
| 政府站改版 | `sources --verify` 能看到哪个源失败；连续失败时早报里的「数据源」段会显示异常 |
| PushPlus 限流/封号 | 额度用不满；真被限就先降群数量，或改用 Bark（iOS，无需注册） |
| 买家用公司 token | 明确要求个人 PushPlus 账号，出事不背锅 |
| 虚假宣传 | 全程不出现"官方""包中签""一定能申请到" |
| 数据转售 | 只做提醒服务，不打包出售原始数据库 |
| 摇号附件解析失败 | 解析失败不影响推送：照样发通告 + 官方 PDF 链接，只是没有人数统计。`lottery --show` 能看到哪些`parsed=false` |
| 预测被当成承诺 | 输出固定带"按公开数据估算"和三个不确定项；客服话术里不出现"稳中""必中" |
| 名单格式改版 | 解析器按"一行一家庭/一家庭多行/Excel 表头"三类识别，新区改版会落到解析失败，不会算出错数 |
| 查询页被爬 | 页面只有认租编号→队列/排位，无姓名无证件号；编号本身不是身份凭证。页面带 `noindex` 且链接按天失效（`?d=`），转发出去的地址第二天打不开；当天转发的仍能用，这是广播群的固有边界 |
| 流程节点漏抓 | `cli batches --days 120` 能看出哪批少了哪一步；源站补发或标题变体会在下一轮 `reclassify` 后补上 |

## 附：技术栈速查

- 抓取：25 个栏目（市级 4 + 区级 21），NFCS 静态页 + gkmlpt JSON 接口

- 存储：SQLite（`data/stockbot.db`），WAL 模式
- 幂等：每条投递有 `delivery_key`，同一批不会重复发
